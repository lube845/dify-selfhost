## 续：非企业版（CE）下的客户端权限闸口补齐

核实结论（解开前一轮的疑点）
- `web/service/share.ts` 头部把 `get` 别名成了 `getPublic`：
  `import { get as consoleGet, getPublic as get } from './base'`。
  所以 `getUserCanAccess(appId, isInstalledApp=false)` 实际请求
  `PUBLIC_API_PREFIX/webapp/permission`（默认 `http://localhost:5001/api/webapp/permission`），
  且 `fetch.ts` 的 `beforeRequestPublicWithCode` 钩子会自动带上
  `X-App-Code: <URL 末段>`。后端 `/webapp/permission` 要求的 appId+appCode 双双满足，
  先前担心的 `raise ValueError("appId must be provided")` **不存在**。
- 后端 `app.py:_check_app_access_permission` 在 `enterprise_identity=False`、
  无 passport 时即可返回 `{result:false, reason:'auth_required'}`，完全 CE-safe。

改动（前端）
1. `web/service/access-control.ts`：`shouldProbe = !isInstalledApp || webappAuthEnabled`。
   公开 webapp 页面（`/chat/<code>`）**无条件**探测 `/api/webapp/permission`，
   否则 CE 下永远拿不到 `auth_required`，`authenticated-layout` 的四态闸口是死代码，
   app store 里的 `userCanAccessApp` 也恒为 true。
   安装版应用仍按 `webappAuthEnabled` 门禁 —— 它走的是
   `/console/api/enterprise/webapp/permission`，CE 下不存在，无条件探测会误报错页。
2. `web/service/base.ts`：
   - 401 分支新增 `web_app_permission_expired` → 跳 `/webapp-permission-expired`。
     **必须放在 `refreshAccessTokenOrReLogin` 兜底之前**，否则 OA 已登录 + 白名单过期的访客
     会被甩到控制台 `/signin`（与该 app 毫无关系的页面）。
   - 403 分支新增 `app_access_permission_denied` → 跳 `/webapp-no-permission`
     （原来只弹 toast；而 webapp 侧查询都是 silent，连 toast 都不会显示）。
   - `ssePost` / `sseGet` 的 401 public 分支同样补上 expired 跳转。
   - 两个错误码只由 `api/controllers/web/wraps.py` 抛出，控制台 API 永不返回，故无需按
     `isPublicAPI` 收窄。

- 后端 5 个权限相关测试文件回归：104 passed。

未决（已向用户说明，等其拍板）

## 续三：修掉一个被本次改动「揭开」的 CE 致命隐患

现象
- CE 下 `GET /api/webapp/permission` 会 **500**。根因：该端点在看
  `features.webapp_auth.enabled` **之前**就无条件调用
  `WebAppAuthService.is_app_require_permission_check(app_id=...)`
  → `EnterpriseService.WebAppAuth.get_app_access_mode_by_id`
  → `EnterpriseRequest.send_request`。而 `EnterpriseRequest.base_url =
  os.environ.get("ENTERPRISE_API_URL", "ENTERPRISE_API_URL")` ——
  全仓库**没有任何地方设置这个环境变量**（已全量搜索确认），于是 httpx 抛出：
  `httpx.UnsupportedProtocol: Request URL is missing an 'http://' or 'https://' protocol.`
  （已用 `uv run --project . python -c` 实跑复现。）

为什么以前没暴露
- CE 下前端 `useGetUserCanAccessApp` 被 `webappAuthEnabled` 短路，从不请求该端点；
  其它调用点（`wraps.py:81/104`、`app.py:134` 的 access-mode、`wraps.py:175/190/194`）
  都正确地包在 `if features.webapp_auth.enabled` 里，只有 `/webapp/permission` 漏了。
- 本轮把前端改成「无条件探测」后，隐患立刻变成真实回归：
  探测 500 → `useCanAccessAppError` → `authenticated-layout` 渲染「应用不可用」，
  即 `/chat/<code>` 直接打不开。

修复
- `api/controllers/web/app.py::AppWebAuthPermission.get`：
  先取 `features`，把 `require_permission_check` 收进
  `... if features.webapp_auth.enabled else False`。
  该值的**每一处使用本来就 AND 了 `features.webapp_auth.enabled`**，
  所以 EE 行为逐字不变，CE 不再触企业调用。
- 回归测试：`test_community_edition_never_calls_enterprise_access_mode`
  （`test_app.py`），把 `is_app_require_permission_check` 的 side_effect 设为
  `AssertionError`，被调到即失败；同时断言仍能返回 `auth_required`。
  5 个测试文件回归 **105 passed**。

顺带确认
- CE 下 `features.webapp_auth.enabled` 仅在 `dify_config.ENTERPRISE_ENABLED` 时置 True
  （`feature_service.py:235-237`），故 `app.py:197` 那个企业分支在 CE 是死代码。
- 可选清理（未动，CE 下不可达）：`app.py:199` 在 `if require_permission_check` 内部
  又调了一次 `is_app_require_permission_check(app_id=...)`，恒为 True，属重复的企业请求。

**教训**：在 CE 自托管仓库里新增/放开前端对 web 端点的调用前，先确认该端点
是否无条件触碰 `EnterpriseService`——`ENTERPRISE_API_URL` 未设置时会抛
`httpx.UnsupportedProtocol`，而不是优雅降级。

## 续六：OA 登录后的权限闭环 + 8 小时重登 + 左下角用户信息

需求（用户原话要点）
1. 登录后权限检查分三态：有权限→正常跳 chat；权限过期→**右上角小窗**提醒联系管理员；
   权限缺失→**右上角小窗**提醒联系管理员。（原来是整页跳 /webapp-permission-expired、
   /webapp-no-permission，要改成 toast。）
2. 每 8 小时要求重新登录。
3. chat 页面左下角加「用户信息 + 退出登录」：可查看登录信息、点击退出回登录页。
4. 不需要登录的场景**看不到**该区块。

后端
- `api/controllers/web/oa_auth.py`
  - `/oa/me` 响应增加 `expires_at`（由 JWT `exp` 经 `_iso_utc()` 转 ISO-8601 UTC）
    与 `session_expire_hours`。前端据此展示有效期 + arm 定时器主动重登。
  - 模块 docstring 同步更新。
- `api/controllers/web/wraps.py` —— **本轮最关键的修复**
  - `_is_signed_in_end_user(end_user, *, system_webapp_auth_enabled)` 语义重写：
    以 **`oa_session` cookie 的存活**为「已登录」信号，不再信 `end_user._is_anonymous`。
  - 原因：`_is_anonymous` 在首次 OA 登录时被置 False 且**永不回滚**，
    所以标签页开着不过期就能一直聊，8 小时重登形同虚设。
  - 例外：EE 下 `webapp_auth` 启用时身份走 SSO/email-code token（无 oa_session、
    end_user 是 `is_anonymous=False`），故仅在 `system_webapp_auth_enabled` 时仍认非匿名行，
    CE 行为不受影响。
- `api/configs/feature/oa_config.py`：`OA_SESSION_EXPIRE_HOURS` 默认已是 **8**，无需改。
- 测试新增 `api/tests/unit_tests/controllers/web/test_oa_auth.py`
  （含 `Max-Age` 窗口、默认 8 小时的产品断言）；`test_wraps.py` 重写，
  有一条既有用例语义**翻转**（非匿名行 + 无 cookie 不再算已登录）。

前端
- `web/service/oa-session.ts`（新）：`fetchOASession()` 用**裸 fetch** 调 `/api/oa/me`。
  刻意不用 `getPublic`——对匿名访客该端点恒 401，走 `base.ts` 的全局 401 处理器会被
  甩到 /webapp-signin 或 /oa-login；这里 401 是「没有 OA 会话」的正常答案。

## 续七：统一「中途权限失效」的右上角提醒

背景：登录时的权限三态已改为右上角 toast，但**会话中途**权限过期/被撤销时仍只跳专用页
（`base.ts` 的 401/403 分支 + `authenticated-layout` 的 expired/denied 分支），
与需求「弹右上角小窗提醒」不一致。

做法：在两个落地页**挂载时**补弹一次 toast。
- `web/app/webapp-permission-expired/page.tsx`、`web/app/webapp-no-permission/page.tsx`
- `useEffect(() => toast.error(...), [t])`，用与登录页**完全相同**的键
  （`oaLogin.permissionExpired.*` / `oaLogin.permissionDenied.*`）和同样的
  `PERMISSION_TOAST_TIMEOUT = 10000`，两边文案逐字一致。
- 页面自身的卡片文案仍走 `webapp.authExpired(Hint)` / `webapp.accessDenied(Hint)`。

为什么要放在落地页而不是跳转前：跳转有两种——`authenticated-layout` 走
`router.replace`（客户端路由），`base.ts` 走 `jumpTo`（整页导航）。后者会销毁旧文档，
在跳转前弹的 toast 必丢。放在目标页挂载时弹则两种都成立。

前提已核实
- `ToastHost` 挂在**根布局** `app/layout.tsx:73`（`timeout={5000} limit={3}`），
  所以独立页（非 shareLayout）也能弹。`toast.error(title, {description, timeout})`
  的 `timeout` 可覆盖根布局默认值。
- 5 个入口全部覆盖：`service/base.ts:582/737/845`（401 → expired 页）、
  `:917`（403 → no-permission 页）、`authenticated-layout.tsx:89-92`（两页）。
- `proxy.ts:17-18` 把这两个路径列入了中间件豁免名单，不会被 OA 拦截。

验证：受限 tsc 类型检查（含这两页 + 登录页 + oa-session + oa-user-info + sidebar）
**EXIT=0**。临时文件已清理。
